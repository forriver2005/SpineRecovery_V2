# 教练模式改造：Codex 总控与模块执行提示词

> 产品需求唯一来源：[12-keep-video-observation-and-coach-product-spec.md](12-keep-video-observation-and-coach-product-spec.md)。复制提示词前先读 12 号。00-06、10、11 号文件是旧稿，不要拿来拼接需求。

## 怎么使用

先把下方“总控提示词”发给一个 Codex 对话。总控应创建一个总目标，再依序创建并运行模块 A → B → C 三个实现对话；每个模块完成并由总控检查患者路径后才启动下一模块。同一个 checkout 里不要并行写代码。当前 Coaching 工作区含用户未提交改动，不能把新 worktree 当作默认方式；只有明确确认包含这些修改的工作区状态确实复制过去时才可用，否则复用当前 checkout 串行执行。绝对不能通过 reset、stash、checkout 或覆盖清理冲突。最终由总控按第 12 号的患者流程做集成。

这些模块是有依赖关系的施工顺序，不是互不相干的架构重写。模块 A 先定义播放节点和目标动作上下文，模块 B 接入同一上下文做正确反馈，模块 C 最后收尾导航。不要同时发给三个 Codex 让它们竞争修改同一场景或控制器。

```text
先在当前工作区检查 git status 和关键场景入口，尊重并保留已有修改。然后按 A、B、C 顺序用 create_thread 创建三个模块实现对话；每次只启动一个子对话，等待它完成和总控检查后再创建下一个。发送下方对应的完整提示词。当前目录有大量已有修改，不能并行写入同一个 checkout；模块应顺序复用当前 checkout。不要用不包含现有修改的新 worktree。

总目标的患者流程：开始前选朝向（默认 A），点现有开始后自动进入动作讲解和完整示范，随后播放原有完整准备语和倒数；按当前处方通路或默认 1 组 4 次逐次跟练。每次都让患者看见当前次数、动作阶段和这次目标侧别，教练在动作相位给方向、保持/呼吸和回位口令。出现稳定偏差时，用项目现有判定能够支撑的具体动作/部位调整语音；无法识别错因时给中性部位提示，不猜诊断。不亮红色错误列表；只有达到现有正确条件的目标部位才变绿。多目标都正确时相关 tracker 在同一个触觉事件内同步震一次。做错、没跟上、追踪未知或 haptic 失败都不能卡住播放。最后给患者“我已学会，进入游戏模式”或“还需要学习，再来一次教练模式”两个选择。

必须逐条保护已有语音、自然语速、pitch、尾音、数字间隔和倒数。时间不够不能删语音、提速、剪尾、压缩停顿、拉长未经允许的承重阶段，也不能把动作是否达标设成播放 gate。长讲解放在动作开始前；短方向 cue 对齐动作前/动作开始；纠错尽量放到最近的安全间隔。新增动作口令由 Codex 编写，并直接使用开发阶段可用的语音生成方式合成为静态 WAV/MP3 资产，接入 Unity 播放；不要要求患者设备实时联网合成，也不要只交台词或待录音表。必须完成当前构建启用的六个动作，不能用死虫/鸟狗两个样例代替其余动作。新增动作表达必须依据项目现有动画、规则/Profile，不杜撰临床含义；只有具体某条纠错在仓库中确无依据时，才单独标待临床确认，不能以此省略该动作其余口令、静态语音或接线。

模块 A：创建一个实现对话并发送下面“模块 A 提示词”。它交付动作教学/播放/语音脚本和可运行的跟练路径后，总控检查，再启动模块 B。

模块 B：发下面“模块 B 提示词”启动一个实现对话。它交付持续观察、患者端正确部位绿显和 tracker 同步触觉后，再由总控验证用户路径并启动模块 C。

模块 C：发下面“模块 C 提示词”启动一个实现对话，完成朝向选择、完成页和路由后，总控只做针对性集成验证。不要新增大型测试框架或把每个异常都写成验收矩阵；选死虫、鸟狗、一个正常结束和暂停恢复作为代表路径即可。

总控最终报告必须区分：已在当前设备上实际看到/听到/触发的结果、只做了代码修改但无法验证的结果、待康复审核台词、缺少游戏路由或硬件同步能力的待办。不能把编译通过、字段存在或同帧发 HTTP 请求写成产品完成。
```

## 模块 A：动作课、播放轴和语音

```text
你负责 SpineRecovery_V2 教练模式的模块 A：让患者真正经历 Keep 式康复动作跟练课。先读：

- D:\Code\SpineRecovery_V2\docs\coach-mode-redesign\12-keep-video-observation-and-coach-product-spec.md
- D:\Code\SpineRecovery_V2\.codex\CODEX.md

不要读 00-06、10、11 号旧方案作为需求来源。先查 git status、正式教练入口、场景和当前播放数据。保留已有未提交修改。用户要求的是明显的患者体验改造，不是加几个 phase/event。

要做出的患者体验：

1. 开始前只有朝向选择；默认 A。点击现有开始后，自动进入该动作的讲解、完整示范、原有准备语和完整倒数，不再加“开始讲解”第二个确认按钮。
2. 讲解要和当前动作绑定。患者先听懂起始姿势、目标部位、方向、保持/回位、呼吸和一个最重要的注意点；教练完整示范一次。讲解/示范不计入四次，也不触发正确绿显或震动。
3. 正式跟练把当前次数（例如 2/4）、动作阶段（准备/抬起/保持/回位/完成）和本次目标侧别清楚显示出来。左右轮换时重新明确说哪只手/腿，不依赖患者记忆。
4. 长讲解提前播；短方向口令落在实际动作开始前或开始点；保持/呼吸和回位口令要对应动作正在发生的相位。当前错误提示“请根据教练演示调整动作”不能算具体教学。
5. 保持所有现存语音完整、自然速度和原 pitch，包含倒数、数字之间停顿、尾音、开始/计数/休息/结束提示。不能为了让台词塞进动画而删减或加速。长内容放到动作前；短纠正若当前段时长放不下，放最近一个回位/休息空档。未经处方/产品批准不得拉长承重/保持时长。
6. 观察和纠正不推进播放，也不等待患者做对。暂停时语音和播放轴一起停，恢复后从当前内容继续；跳过或重播时清掉过期语音，不重复计次。

真实场景对照（必须确认正式入口，不要只改 JSON）：

- 死虫和鸟狗现有 Practice 场景各是开始、抬起1/放下1 … 抬起4/放下4、结束，共 10 段；抬起约 5 秒、回位约 2 秒，死虫现有回位间隔 4 秒。
- 第1/3次目标右臂+左腿（activeRegions=6）；第2/4次左臂+右腿（activeRegions=9）。按这四次真实顺序显示次数和侧别。
- 场景 voiceClip 目前为空；资源里只有通用介绍、准备倒数、开始、数字、保持、通用调整、下一动作和提示音。死虫/鸟狗专属目的、方向、回位和纠正口令/音频尚未制作。
- 同名的单段 JSON 动作包和 Practice 场景 Animator 分段不是同一播放路径。先确认当前入口。

内容交付：为六个当前构建启用动作（死虫、鸟狗、臀桥、卧位猫式、侧桥、卷腹）分别完成专属台词、播放节点、项目内台词依据、生成工具/模型、音色/语速、音频资产路径和实际时长。六个动作每项都要写清并接入：起始提示；每个主要动画相位的目标/方向口令；保持或呼吸口令（仅在项目动作规则支持时）；回位口令；错误状态稳定时点名当前诊断暴露的目标部位，并给该动作专属的简短调整句。现有诊断只知道哪一部位偏离时，用中性调整句（例如“右腿按教练示范调整”）；不能猜患者是过高还是过低。死虫、鸟狗要逐次写明四次左右侧别；臀桥、卧位猫式、侧桥、卷腹必须按各自正式场景相位单独编写，不能共用占位文案。Codex 直接用开发阶段可用的语音生成方式制作统一、自然的普通话静态 WAV/MP3，放进 Unity 可导入目录，保存台词源文本和可重复生成方法，并在正式场景接线播放；不增加运行时 TTS 云 API。已有音频保持原样；新旧音频不混剪、不调快，也不能为塞进动画而加快新语音。Keep 官方动作页只参考讲解结构（步骤、呼吸、动作感觉、常见错误和修正），不复制大众健身口令为康复医嘱。台词必须基于项目对应动画、动作 Profile 和现有 Coaching 判断。只有仓库对某条纠错确实没有任何判定依据时才把该句单独标为待临床确认；这个状态不能替代六个动作其余台词、音频生成和场景接线。每个动作实际听到专属合成语音才算完成。

完成时交出改动清单、六个动作逐项内容/音频/播放节点表、死虫/鸟狗逐次播放记录、现有倒数与语音完整保留说明，并在代表性可运行场景证明数字/侧别/动作口令对得上当前动作。六项都必须实现；运行核对抽查死虫、鸟狗和一个腰背动作即可，不建新测试框架或扩成长矩阵。
```

## 模块 B：连续观察、绿色和同步震动

```text
你负责 SpineRecovery_V2 教练模式模块 B：让做对的身体部位即时变绿并同步触觉确认。先读：

- D:\Code\SpineRecovery_V2\docs\coach-mode-redesign\12-keep-video-observation-and-coach-product-spec.md
- D:\Code\SpineRecovery_V2\.codex\CODEX.md

保留工作区现有修改。先确认死虫/鸟狗正式 Practice 场景使用的当前 Coaching 几何条件和 tracker 路由。不得更改临床阈值、借用游戏 70 分线或编新规则。

产品定义写死如下：

- 观察持续读取姿态；不只在特定时间区间评分，不显示分数，不驱动播放次数或时长。
- 患者端只设计正确目标部位绿显。绿色只能由本动作明确的正向正确条件驱动：当前目标有效、属于本次动作且通过现有正确/清除条件（如 `shouldClear`）；未知、无效追踪、非目标和滞回区一律不绿。不能简单写成 `!isRed` 或将“没有错误候选”直接当正确。若规则只有二值完备错误判据且无独立正确条件，先核实其覆盖全部有效状态并在动作映射表写明证据，不能默认取反；没有红色错误列表/红色错误高亮。
- 死虫/鸟狗还要沿用当前 Coaching 几何正确判断；每次只把该次目标侧别的部位当目标。不得把“没有错误候选”当正确；有效性、滞回、阈值和追踪未知必须避免误绿。
- 多目标都变绿时，所有对应 tracker 由同一个触觉事件同步震一次；不能一个接一个、固定周期重复震，绿色保持正确时也不能重复震。本次所有目标未同时正确时不震。
- 绿显和播放独立：传感器未知不挡播放，haptic 失败不撤绿也不挡播放。

检查目前 tracker 接口能否实现真正同步。若设备协议支持预约同一触发时间或组命令，就通过同一逻辑触觉事件发出；如果只有每个 tracker 各自 HTTP 请求，必须测量真实设备起振差并如实报告，不可把“同一帧启动多个请求”描述为同步完成。不要静默串行发送。

完成时给出死虫左右交替样例的一条可运行路径：目标部位未到阈值时不亮；全达标时对应目标变绿并同时震一次；追踪无效时不误报；四次节奏始终继续。报告实际设备测试与硬件未验证项。只做必要的小范围验证。
```

## 模块 C：朝向选择与结束去向

```text
你负责 SpineRecovery_V2 教练模式模块 C：实现开始前两种朝向比较，并让完成后的选择适合“先学再玩”。先读：

- D:\Code\SpineRecovery_V2\docs\coach-mode-redesign\12-keep-video-observation-and-coach-product-spec.md
- D:\Code\SpineRecovery_V2\.codex\CODEX.md

保留工作区已有修改。产品定义：

- 开始训练前有两档选择，默认 A，用户能清楚看出哪档被选中。训练开始后不提供切换按钮。
- A：训练中持续跟踪用户模型朝向，让教练平滑转到同一朝向；两模型在画面里朝同一个方向，不是互相面对。
- B：教练固定在场景朝向，旋转用户显示模型让它朝向和教练一样，无论用户实际上转向哪里。
- 朝向只处理画面模型，不能变更传感器输入、阈值或姿态判断。重练时重置会话并重新选择。
- 正常完成页只强调“我已学会，进入游戏模式”和“还需要学习，再来一次教练模式”。进入游戏使用现有对应动作路由；重练重播当前动作并回到朝向选择。不要只改按钮字样而保留一排旧菜单作为同等主入口。
- 非正常中断不能伪装成完成。卧位患者完成死虫/鸟狗不能因为必须站起或某条不相关语音忙碌而无法看到正常完成选择。
- 如存在教练动作没有对应游戏路由，不要删掉动作或伪造跳转；列出具体动作、当前路由和需要产品决定的去向。

完成时用 A/B 两个模式各走一遍，并走通一个“进入游戏”和一个“再练教练”路径；有 UI 限制、游戏场景缺失或无法实际验证时准确报告。不要改变游戏内训练模式。
```
